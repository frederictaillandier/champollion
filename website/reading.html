02 · Desktop Jetson

Reading the screen

Every recorded frame has to be read: which words are on screen, where, and how sure the reader is. Tesseract did it on the desktop until 16 October. Since then a GPU reader on a Jetson board reads the recordings faster than they're made, without taking anything from the game.

The problem

The desktop can't read while you play

The daemon reads finished recordings with Tesseract, on threads that only get the CPU time the game leaves (SCHED_IDLE), and with a single reader while the game runs. On 14 October the first 2-minute file took 12 minutes to read during play. Once the game closed, two readers caught up at about 2 minutes 15 seconds per file. Tesseract itself isn't slow: one Ryzen core reads a frame in 0.19 s. The game just needs those cores.

The Jetson

A spare board on the LAN

The Jetson AGX Xavier sits at 192.168.0.43 (tegra-ubuntu.local): 8 ARM cores, 30 GB of memory, a 512-core GPU, and a hardware H.265 decoder. It runs Ubuntu 20.04 with JetPack 5.1.6. Nothing it needed was installed, and sudo asks for a password, so everything went into the user's home folder:

GPU OCR, explained

No training, no labelled data

OCR here means two trained models, downloaded ready to use. PaddleOCR's PP-OCRv5 has a detector, which marks where text is, and a recognizer, which reads one line at a time. Its Latin recognizer covers Czech, Č Ě Ř Ů included.

The model: the recipe

Millions of numbers learnt from labelled text by the people who trained it. Like Tesseract's ces.traineddata, which also came ready-made.

ONNX: the recipe's format

A standard file format for trained models, so they can run outside the tool that trained them. Like PDF for documents.

TensorRT: the kitchen

NVIDIA's engine for running any model fast on their GPUs. It knows nothing about text: trtexec compiles each ONNX file into an engine tuned for this exact GPU.

What was learnt

Five things that didn't work the first time

Half precision broke the big detector

Built in FP16, PaddleOCR's large "server" detector lost whole menu items: "Nová hra", "Nastavení" and "Autoři" never lit up in its map. In FP32 it read everything, even the gothic logo, but took 458 ms. The small "mobile" detector reads as well in 52 ms.

Resizing was slower than the GPU

The image crate took 140 ms to scale one 2560×1440 frame on the ARM cores, against 57 ms of detection on the GPU. fast_image_resize, which uses the CPU's vector instructions, brought it down to a few milliseconds.

A flexible engine never finished

Asking TensorRT for one engine fitting any frame up to 2560×1440 took 21 GB of memory and was still tuning after 29 minutes. A fixed input size builds in under 20.

Libraries found at build time, lost at run time

TensorRT needs libcudla.so.1, which the program didn't find although its own search path listed the folder. That path was RUNPATH, which doesn't apply to a library's own dependencies; --disable-new-dtags makes it RPATH, which does.

The official model wasn't better

PaddlePaddle's own Latin recognizer knows 836 characters, against 502 in the community conversion. It found 281 confident words instead of 282, merged some (playedkingdom) and read 15 ms slower.

Tuning

More workers, smaller frames

Each worker thread loads its own copy of the engines. With one worker, the GPU waits while the CPU scales frames and spells words; a second worker fills those gaps. After that the GPU is busy all the time and more workers only queue for it. In its 30 W mode the Jetson already lets the GPU run at 1,339 of 1,377 MHz, so full power wouldn't change much.

Detecting on frames scaled to 960 wide instead of 1280 made reading 30% faster and lost only small English text from Steam's overlay; matched against the game's text, both found the same 31 Czech lines. Smaller recordings help a little more, and at every size tested the same Czech lines were found. 720p isn't faster than 1080p and misreads small text more, hence 1080p at 8 frames per second.

Quality

About as good as Tesseract, with different mistakes

On 120 frames from 14 October, both readers found about 300 distinct words with confidence 70 or more, 230 of them in common. The GPU reader reads far less junk from scenery (about 9 lines per frame; on one 6 October frame over scenery, Tesseract reported 42, mostly garbage), but sometimes drops a Czech accent. The same words are read correctly in other frames, so the errors come and go; adding a margin above and below lines didn't help.

In use

How the desktop and the Jetson work together

No service runs on the Jetson and nothing is stored there. When a 2-minute recording is finished, the daemon on the desktop starts the reader over SSH and streams the file to it:

ssh 192.168.0.43 '~/ocr/read-recording 8' < 23-29-43_000.mkv
  1. The Jetson reads every frame8 per second, as recorded, on the GPU; the recording sits in a temporary file only while it's read.
  2. It corrects each line with the game's textA copy of the localization database sits in ~/ocr/game-text.sqlite; lines found there come back with their exact Czech.
  3. It sends back each frame's text, in orderOne JSON object per frame, holding the text in Tesseract's own format, so the daemon parses it with the code it always had.
  4. The desktop carries on as beforeWord tracking, the vocabulary and card making are unchanged. Only the frames saved for reference are decoded locally, about 2 seconds each.

Tesseract is gone

Once the Jetson had read its first sessions, the daemon's own reading path and its Tesseract dependency were removed (17 October). The daemon keeps only the parser for Tesseract's text format, which is how it reads the Jetson's results. Without the Jetson, recordings wait: no text is read on the desktop any more.

Set with CHAMPOLLION_OCR_REMOTE=192.168.0.43 and CHAMPOLLION_OCR_FPS=8 in the daemon's service. On the Jetson, ~/ocr/read-recording is gpu-ocr/jetson/read-recording; it loads the engines (about 17 seconds) and the game's text (about 1 second) for each recording.
