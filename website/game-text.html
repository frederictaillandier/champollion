The game's own text

Kingdom Come: Deliverance II ships every line it can show, in Czech and English. OCR still decides what you saw and when; each line it reads is then replaced by the game's exact text. Misread accents come back, and you still only learn what was on your screen.

The files

204,083 lines, each with an ID

Localization/Czech_xml.pak is a zip archive of eleven XML tables, one row per line of text: an ID, then two Czech versions. English_xml.pak has the same IDs, so every line comes with the game's official English. Texts carry a little markup (<br/>, <paragraph>, <accent>), removed on import.

Two Czech versions of most dialogue

In 71,258 dialogue rows the two Czech columns differ, the second often with spoken forms: "Pořád nevím, kde hledat Hanse" against "Pořád nevim…". Which one the subtitles show isn't known yet, so both are kept and matched.

The log doesn't help

The game's kcd.log only records startup, DLCs and fonts: nothing about dialogue or quests. Reading the screen stays the only way to know what you saw.

champollion-game-text import ~/.steam/steam/steamapps/common/KingdomComeDeliverance2/Localization \

Matching

Finding a line despite OCR errors

A screen line rarely equals a game line: OCR drops accents and confuses letters, subtitles wrap over several lines, and a save name comes with its playtime and date. Matching compares texts loosely, then hands back the exact one.

The lines that don't match are text the game files don't hold: the main menu's news panel, the Deep Silver account promotion, and Steam's overlay. Dropping them loses nothing worth learning. Matching also made the cheaper settings safe: detecting at 960 wide, or reading 1080p recordings, found exactly the same Czech lines.

In use

Inside the reader, on the Jetson

Since 16 October the matching runs on the Jetson, inside the GPU reader, before any text is sent back: the desktop only ever sees corrected lines. A copy of the database sits in ~/ocr/game-text.sqlite, loaded in about a second for each recording, and a cache per line makes the dozens of frames of one subtitle free.

The 10 wrong sightings (ceské, svym, uveznen…) were fixed by hand on the backend: 7 duplicated a correct sighting and were deleted, 3 had their form corrected. Claude had already found the right dictionary forms, so no duplicate card was made.

133 MB, not 360

The index first kept every line twice, with tables of character positions: 360 MB. It now keeps each line's text and its three-letter index only, and rebuilds the rest for the 40 candidates it compares. Same results, same speed.

Why not let SQLite search?

SQLite reads the file as needed, but its full-text search wants every three-letter sequence present, and one misread letter breaks it. Counting shared sequences in memory tolerates errors.

After a game update

Import the text again on the desktop, where the game is, and copy the file to the Jetson: champollion-game-text import …, then scp … 192.168.0.43:ocr/game-text.sqlite.

Known limits

Some game lines are the same in both languages (Home, Activity) and could be skipped. A short wrapped line can match a shorter game line with the same words instead of its real source: "nepřátele…" matched the dog command Útočí na nepřátele. The other lines of the same frame could settle it.
