01 · Desktop

Recording and the study lock

champollion-daemon runs as a user service on the desktop. It waits for Kingdom Come: Deliverance II (Steam app 1771300), records the screen while it runs, and closes it when too many cards are waiting.

Capture

From the screen to 2-minute files

The desktop's screen-sharing portal hands the daemon a PipeWire stream. The first time, it asks which screen to share; the choice is remembered in ~/.local/state/champollion/. Frames then stay on the graphics card all the way to the file: scaling and colour conversion run as OpenGL shaders, and encoding runs on NVENC, a chip of its own on the RTX 3070, so the game barely notices.

SettingDefaultWhat it does
CHAMPOLLION_FRAMERATE8Frames per second recorded. Was 15 until 15 October; the reader never used more than 8.
CHAMPOLLION_MAX_HEIGHT1080Frames taller than this are scaled down, keeping the screen's proportions. 0 records at full size.
CHAMPOLLION_QP20Encoder quantizer, 0 to 51: lower keeps text sharper but makes bigger files.
CHAMPOLLION_SEGMENT_MINUTES2Length of each file. A file is read once it's finished, and a crash only loses the current one.
CHAMPOLLION_APP_ID1771300The Steam game to watch.
One evening

How big the files get

The session of 14 October, still recorded the old way: full 2560×1440 at 15 frames per second. Sizes swing with what's on screen, since the encoder keeps a constant quality rather than a constant bitrate: the first file, mostly menus, is the smallest, while moving scenery costs far more.

The .mkv files were really MP4.

Every recording until 16 October began with an MP4 ftyp box. splitmuxsink creates its muxer as soon as it is linked, which happens while the pipeline description is parsed; the recorder chose Matroska afterwards, too late, first by handing it an element, then by naming its factory. A test with both orders confirmed it. The muxer is now named in the description itself (splitmuxsink muxer-factory=matroskamux), and recordings are Matroska since 16 October, 23:29. It matters because Matroska stays readable up to the last frame if the daemon is killed mid-file.

Time to study

The study lock

Every 30 seconds the daemon asks the backend how many cards are due. Two thresholds, far apart, decide what happens. If the game unlocked just under 50, it would lock again a few minutes into playing.

A word counts a few minutes after it was on screen: its 2-minute file has to finish, be read, then be made into a card. By the next morning, 229 cards were due.
